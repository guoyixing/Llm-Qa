# 代码规范配置说明

本目录存放供大模型语义读取的代码审查规则，不依赖解析器或静态分析器。`common/` 保存所有项目默认采用的公共规则，`projects/` 保存按项目补充或覆盖的规则。

## 规则级别

- `REQUIRED`：有明确规则标签、明确适用范围和可核验依据的强制要求。违反时可以报告规范违规。
- `ADVISORY`：建议或尚未配置的偏好。违反时只能给出改进建议，不能报告规范违规，也不能据此判定审查失败。

任何没有明确规则标签和可核验依据的口头偏好、示例写法、推测惯例或未配置选项，只能按 `ADVISORY` 处理。规则级别缺失或含义不清时，也按 `ADVISORY` 处理。

## 规则标签

规则标签用于在 Markdown 规范和代码质量报告中定位规则，格式为 `<类别>-<三位序号>`。四类质量规则分别使用 `STYLE`、`READ`、`ROBUST`、`PERF`，例如 `PERF-001`。标签只承担 Markdown 引用作用，不参与稳定问题 ID 的计算，也不绑定历史记录或问题生命周期。

项目规则标签使用 `<PROJECT_ID>-<类别>-<三位序号>`，其中 `<PROJECT_ID>` 必须来自 `AGENTS.md` 项目表的 `project_id`，例如 `api-PERF-001`。真实项目规范由使用者配置，本仓库不预设任何组织规则。

## 可复制的规则模板

每条规则必须完整填写以下字段。字段内容使用中文，技术标识符可保留原文。

```markdown
### <规则标签> <规则标题>

- 标签：<用于 Markdown 引用的规则标签>
- 级别：<REQUIRED 或 ADVISORY>
- 适用范围：<语言、目录、文件、组件或调用场景>
- 规则：<必须做到或建议做到的具体行为>
- 例外：<允许例外的条件；没有例外时写“无”>
- 检查重点：<审查时需要核对的证据>
- 建议：<发现问题后的具体修改方向>
- 来源：<公共规范、项目约定、官方文档或决策记录的可定位引用>
```

## 公共规则与项目规则的覆盖原则

1. 先读取 `standards/common/` 下适用于本次审查的公共规范，再读取 `AGENTS.md` 项目表中对应的项目规范目录。例如，`api` 对应 `standards/projects/api/`。不得在本文件另行定义平铺文件布局。
2. 对同一规则主题，项目规范只有在显式引用项目规则标签与公共规则标签、说明冲突内容和覆盖理由时，才能覆盖公共规范。
3. 不冲突的公共规则与项目规则全部累加生效。项目规范没有明确覆盖声明时，公共规范继续生效。
4. 规范相互冲突且无法按上述规则决断时，必须记录配置错误并停止受影响规则的判断，不得生成确定性违规结论。
5. 优先级固定为 `common -> project`，后加载的项目规范仅在显式覆盖时优先。没有规则标签和可核验依据的偏好只能形成 `ADVISORY` 建议，不能形成规范违规。

## 项目允许例外示例

以下内容仅演示格式，不代表真实项目规范。示例项目 ID 与目录分别来自 `AGENTS.md` 项目表中的 `api` 和 `standards/projects/api/`：

```markdown
### api-PERF-001 小批量预加载允许逐项查询

- 标签：api-PERF-001
- 级别：REQUIRED
- 适用范围：api 项目的启动阶段，且配置项数量不超过 10 条
- 规则：项目规则 `api-PERF-001` 显式覆盖公共规则 `PERF-001`。冲突内容是公共规则禁止循环内逐项数据库读取，而本规则允许满足适用范围的读取；覆盖理由是启动阶段数据量有严格上限且不受请求量放大。
- 例外：仅限启动阶段的只读预加载；数量超过 10 条或进入请求处理路径时恢复 PERF-001。
- 检查重点：确认调用阶段、数据上限、只读属性，以及不存在请求量放大。
- 建议：在代码附近保留可定位的配置上限，并在范围变化时改为批量查询。
- 来源：示例项目决策记录 <路径或链接占位符>
```

若没有显式引用双方规则标签、说明冲突内容和覆盖理由，就不构成有效覆盖，公共规范继续生效；冲突无法决断时按配置错误处理。没有规则标签和可核验依据的偏好只能作为 `ADVISORY` 建议。

## 维护要求

- 新规则先选择便于在当前 Markdown 中定位的标签，再复制模板填写全部字段。
- 规则应描述可观察行为，避免使用“代码要优雅”一类无法核验的表述。
- 来源必须能让审查者找到依据，不能填写无法定位的“团队共识”。
- 修改规则时检查规则正文、来源和项目覆盖是否仍然成立；标签变更只需同步当前 Markdown 中的引用。
