# 公共编码风格规范

本文件定义跨项目默认采用的编码风格。规则 ID 以 `STYLE` 开头，必须保持唯一和稳定。未在本文件或有效项目规则中配置的格式偏好只能作为 `ADVISORY` 建议。

## 可复制的规则模板

```markdown
### STYLE-<三位序号> <规则标题>

- ID：STYLE-<三位序号>
- 级别：<REQUIRED 或 ADVISORY>
- 适用范围：<具体范围>
- 规则：<具体要求>
- 例外：<明确条件或“无”>
- 检查重点：<核对证据>
- 建议：<修改方向>
- 来源：<可定位来源>
```

### STYLE-001 名称表达用途

- ID：STYLE-001
- 级别：REQUIRED
- 适用范围：变量、函数、类型、模块、配置项和持久化字段的新增或修改
- 规则：名称必须表达业务用途或技术职责，同一概念在同一作用域内使用一致术语，不得使用无法说明含义的临时缩写或误导性名称。
- 例外：语言惯例中的短名称，以及作用域极小且含义明确的索引变量可以保留。
- 检查重点：名称是否与实际值、返回结果、副作用和单位一致，重命名后引用是否同步。
- 建议：优先使用领域词汇和带单位的名称，把布尔值命名为可判断的状态或条件。
- 来源：公共规范 `standards/common/coding-style.md`

### STYLE-002 日志可定位且不泄露敏感数据

- ID：STYLE-002
- 级别：REQUIRED
- 适用范围：应用日志、审计日志和诊断输出
- 规则：日志必须包含定位事件所需的稳定上下文，并使用与影响相符的级别；不得记录密码、令牌、完整凭据、私钥或未经脱敏的个人数据。
- 例外：无。
- 检查重点：日志级别、事件标识、项目或请求上下文、敏感字段脱敏、失败日志是否保留根因。
- 建议：使用结构化字段记录稳定标识，避免拼接大对象、重复日志和只有“失败”而没有上下文的消息。
- 来源：公共规范 `standards/common/coding-style.md`

### STYLE-003 异常处理保留根因和语义

- ID：STYLE-003
- 级别：REQUIRED
- 适用范围：异常捕获、转换、记录和重新抛出
- 规则：捕获异常后必须处理、转换为更明确的领域错误或保留根因重新抛出，不得静默吞掉异常，也不得用无关成功结果掩盖失败。
- 例外：明确允许忽略且不会改变结果的清理操作，可以忽略指定异常，但必须在代码中说明原因和边界。
- 检查重点：捕获范围是否过大、根因是否保留、错误信息是否准确、调用方是否能区分失败类型。
- 建议：缩小捕获范围，使用带原因链的异常转换，并让返回状态与实际执行结果一致。
- 来源：公共规范 `standards/common/coding-style.md`

### STYLE-004 文件和函数结构围绕单一职责

- ID：STYLE-004
- 级别：REQUIRED
- 适用范围：新增或显著修改的文件、类型和函数
- 规则：代码结构必须让入口、核心逻辑和依赖边界可辨认；一个单元不应混合无关职责，也不得通过深层嵌套隐藏主要流程。
- 例外：框架要求的注册文件可以集中声明多个同类入口，但业务实现仍应分离。
- 检查重点：职责数量、依赖方向、重复分支、嵌套深度，以及修改一个需求是否迫使无关逻辑同时变化。
- 建议：按职责提取小单元，使用早返回减少嵌套，并把外部交互放在清晰边界中。
- 来源：公共规范 `standards/common/coding-style.md`

### STYLE-005 通过 import 引用类

- ID：STYLE-005
- 级别：REQUIRED
- 适用范围：本次提交新增或修改的、支持 `import` 机制的源代码中的类型引用
- 规则：引用其他包或命名空间中的类时，必须在文件的 `import` 区域导入并使用简单类名，不得在类声明、字段、方法、注解、泛型或可执行语句中直接书写全限定类名。
- 例外：同一文件确实需要引用两个或以上简单名称相同的类时，可以仅对发生名称冲突的类使用全限定类名。
- 检查重点：检查提交差异中新增或修改的类型引用是否包含包名或命名空间前缀，并核实保留全限定类名的位置是否存在真实的简单类名冲突。
- 建议：把无名称冲突的类移到文件的 `import` 区域，并将使用位置改为简单类名；存在名称冲突时，仅在必要位置保留全限定类名。
- 来源：公共规范 `standards/common/coding-style.md`
